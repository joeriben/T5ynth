Csound and its audio-file libraries, as bundled with akróasys
=============================================================

akróasys plays its language-resonant oscillator (LRO) through Csound: the
orchestra code that an LRO sound consists of is compiled and run by the Csound
library at runtime. That library therefore travels with the application. Where
it sits depends on the platform:

  macOS
    Contents/libs/CsoundLib64            the Csound library itself
    Contents/libs/Opcodes64/*.dylib      Csound's plugin opcodes
    Contents/libs/lib*.dylib             the audio-file libraries Csound needs
    Contents/libs/rawwaves/*.raw         STK's wavetable data, read by the STK
                                         opcodes in Opcodes64/libstkops.dylib

  Windows
    csound64.dll                         the Csound library itself
    plugins64/*.dll                      Csound's plugin opcodes
                                         (beside akroasys.exe, and inside the
                                          VST3 at Contents/x86_64-win)

Csound is a shared library here, never statically linked into akróasys, and
nothing is modified. On macOS each file is the shared library as built by its
own project with only its recorded load paths rewritten, so that it resolves
inside the bundle instead of in a system-wide location. On Windows the files are
the Csound project's own release binaries, byte for byte.


What is bundled, and under which licence
----------------------------------------

  Csound 6.18.1               LGPL-2.1-or-later   https://csound.com
                                                  https://github.com/csound/csound

On macOS one further set of files travels with Csound and is not Csound: the
wavetables of the Synthesis ToolKit in C++ (STK) by Perry R. Cook and Gary P.
Scavone. Csound's STK opcodes are a wrapper around STK's own instrument classes,
and those classes read their excitation and waveform data from files at run time.
The opcode module refuses to register at all unless it is told where they are, so
the data ships with it, unmodified.

  STK 5.0.1 (rawwaves only)   MIT-style, see     https://ccrma.stanford.edu/software/stk/
                              STK.txt beside      https://github.com/thestk/stk
                              this file

  (Only the 41 .raw data files are bundled — none of STK's own source, which
  akróasys does not build against. Csound's libstkops module, which does, is
  part of the Csound payload above.)

The audio-file libraries Csound uses come with it differently on the two
platforms, and at different versions. On macOS they are separate shared
libraries next to CsoundLib64; on Windows the Csound project links them into
csound64.dll itself, and akróasys ships that release binary unchanged.

Replacing the Csound library with your own build
------------------------------------------------

The LGPL asks that you be able to run this application against your own version
of the library. You can. akróasys uses the Csound 6 C API — csoundCreate,
csoundCompileCsdText, csoundPerformKsmps and the named-channel calls — so a
6.18.x build of your own will do.

macOS:

  1. Record the load path this bundle expects:

         install_name_tool -id @loader_path/../libs/CsoundLib64 CsoundLib64

  2. Put it in place of Contents/libs/CsoundLib64. If your build needs plugin
     opcodes of its own, replace Contents/libs/Opcodes64/ with yours as well —
     akróasys points Csound at whatever that directory contains, and at
     Contents/libs/rawwaves/ for the STK data, which you can replace the same
     way. That directory must stay complete: an STK opcode that asks for a file
     that is not there aborts the process rather than falling silent.

  3. Re-sign the application. Replacing any file inside the bundle invalidates
     its signature, and macOS refuses to load a library the signature does not
     cover:

         codesign --force --deep --sign - akroasys.app

     That is the whole procedure — this re-signed application no longer runs
     under the hardened runtime, so nothing checks who built the library.
     macOS will treat the application as one you built yourself: open it once
     from the Finder's context menu if Gatekeeper asks.

Windows:

  Replace csound64.dll next to akroasys.exe (and the copy inside the VST3 at
  Contents/x86_64-win) with your own, and plugins64/ with your own plugin
  opcodes if you have them. akróasys loads that file by name from its own
  directory and asks Csound to use the plugins64 directory beside it, so no
  registry entry, PATH change or environment variable is involved.
